- Review findings (2026-10-11, source inspection): `GET /api/venues/{id}/map-draft/` is generated by `_map_draft_payload`; `PUT` validates and atomically replaces venue-scoped rows. Nodes expose `id`, normalized `x`/`y`, and properties. Edges expose `id`, both `from`/`to` and `from_node`/`to_node` FK IDs, `length_m`, `direction`, `closed`, `accessible`, and `access_rules`. Normalize endpoint IDs to `from_node`/`to_node` when calling `find_route`; its other needed edge fields are already present. `MapFeature` exposes `id`, `name`, `category`, `status`, and `properties`; status is constrained to `open`, `closed`, or `delayed`, so the adapter may map `status == "open"` to the helper's strict boolean. Optional wait can be read from `properties.waitMinutes` if authored; malformed values are excluded by `suggest_next_place`. No `access_node_id`/feature-to-node relationship is represented, so place suggestions cannot be safely connected yet. Contrary to an earlier plan assumption, `PathEdge` has no geometry field and the payload returns no edge geometry. `POST /api/route` exists but is still a 501 stub. Docker API probing was unavailable because access to the Docker Desktop named pipe was denied; findings are from source, not a live response.
