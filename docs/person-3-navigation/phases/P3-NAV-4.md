# P3-NAV-4 — Approximate manual start (optional)

Owner: Person 3 — Navigation

Owned paths: `api/venueflow/routing.py`; this phase document

Shared dependencies: [P3-NAV-3](P3-NAV-3.md), [Person 3 brief](../BRIEF.md), [shared contract](../../SHARED_CONTRACT.md), integration confirmation of the visitor's start-point input shape

- Status: `not started; optional; plan detailed`
- Goal: Let the visitor use a manually selected map point as an explicitly approximate start by mapping it to a nearby graph node.
- Scope: Only after P3-NAV-1 through P3-NAV-3 are verified, add a pure helper that chooses the nearest node from supplied comparable plan coordinates, returns the node ID and an explicit approximate label, and reports when no acceptable node is available. This is not GPS processing or GPS snapping.
- Acceptance criteria:
  - [ ] Integration confirms the coordinate representation and caller needs before implementation.
  - [ ] A fixture maps a point to the expected nearest node using a documented distance unit/coordinate scale and deterministic tie rule.
  - [ ] Empty graphs or points beyond any documented maximum distance return an explicit failure.
  - [ ] Output labels the result as approximate.
  - [ ] Malformed points/nodes and non-finite coordinates fail explicitly without leaking incidental exceptions.
  - [ ] Inputs are not mutated; implementation remains standard-library-only and does not import Django or change `find_route`/`suggest_next_place` behavior.
- Checks: Inspect the current `routing.py` contract and integration caller first. Then run focused plain-Python fixtures for nearest node, exact tie behavior, empty graph, malformed/non-finite coordinates, distance-limit boundary, beyond-limit input, approximate labeling, and unchanged existing routing helpers; run `python -m compileall -q api/venueflow/routing.py` and `git diff --check`. No Django settings or database are required.
- Dependencies: P3-NAV-3 and integration confirmation; otherwise skip this optional phase.
- Out of scope: Continuous GPS, location permission, latitude/longitude projection, path snapping, and claims of position accuracy.
- Implementation plan:
  1. **Resolve the boundary before coding.** Ask integration to confirm how the visitor chooses a point (for example, click coordinates relative to the rendered plan), coordinate field names and scale, whether node and click coordinates share the same origin/orientation, the caller's required success/failure fields, and a defensible maximum snap distance. The shared contract stores normalized `plan_x`/`plan_y`, but that alone does not establish the visitor input representation or a safe threshold. Do not implement if the caller shape or maximum-distance policy remains unknown; keep this optional phase skipped and report the dependency.
  2. **Freeze a pure helper contract in this phase document before implementation.** Recommended input is an iterable of node mappings with stable `id`, `plan_x`, and `plan_y`, plus one point mapping using the same coordinate space and an explicit maximum distance in that space. Recommended helper name: `nearest_node_for_manual_start(nodes, point, max_distance)`. Confirm the public name and output shape with integration before coding. Success should include `ok=True`, selected `node_id`, measured plan-space distance, distance unit/scale metadata or documentation, and `approximate=True`; failure should have `ok=False`, a stable reason such as `invalid_input`, `no_nodes`, or `too_far`, null selection/distance, and a useful message. Keep keys compact and stable for the caller.
  3. **Define coordinate and distance semantics.** Use Euclidean distance only within the confirmed shared plan coordinate space; document whether values are normalized image units or another scale. Do not call this meters unless confirmed by calibration. Select the nearest node whose finite distance is at or below the confirmed maximum. Treat an exact threshold match as acceptable. Never compare plan coordinates with latitude/longitude, infer coordinates from graph connectivity, or snap to an edge/path.
  4. **Validate without weakening current routing contracts.** Validate top-level iterability and point/node mapping shape, require finite numeric coordinates (reject booleans and numeric strings), and skip malformed individual nodes so one damaged record does not mask a valid nearest candidate. Exclude missing/empty node IDs. If IDs are duplicated, exclude all occurrences of the duplicated ID to avoid ambiguous selection. Return an explicit failure when the point is malformed, the graph has no usable nodes, or no candidate is within the cap. The exact policy for malformed top-level input must be stable and documented.
  5. **Make selection deterministic and side-effect free.** Compare full-precision distances; for exact ties, preserve the first valid node in input order. Do not add hidden preferences or sort by ID. Materialize a one-shot node iterable at most once, do not mutate caller records, and keep the module standard-library-only. Leave `find_route` and `suggest_next_place` signatures, route choice, and outputs untouched.
  6. **Verify each acceptance case with focused fixtures.** Cover a known nearest-node selection, tie order, normalized scale/distance calculation, exact maximum-distance boundary, a point just beyond the maximum, empty/all-invalid graph, malformed point, malformed/non-finite node coordinates, duplicate IDs, generator input, result labeling as approximate, and no mutation. Re-run any existing relevant routing fixtures or direct regression checks to ensure prior helpers remain unchanged; use only repository-declared commands and do not introduce a test framework.
  7. **Close the phase with evidence and integration handoff.** Update this document's status and verification record only after checks pass; record unresolved cases honestly. Update `CHANGELOG.md`, `AI_USAGE.md`, and `handoff.md`; update `README.md` only if setup or user-facing demo instructions change. Review and stage only phase-owned files plus the required records, then commit the completed phase. Tell integration the finalized helper signature, result shape, units, max-distance policy, and limitations. Do not wire API/page/model changes in this navigation phase.
