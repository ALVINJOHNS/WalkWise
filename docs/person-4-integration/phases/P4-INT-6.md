# P4-INT-6 — Link place features and route published snapshots

- Status: verified
- Goal: Add an explicit feature-to-path-node link to authored and published venue data, then serve route requests computed only from the selected venue's latest published snapshot.
- Scope: Integration-owned models, migration, map-draft serializer/view, the minimal event publish API needed to create `MapVersion` rows, route DRF view/serializer, and focused integration documentation. Keep Person 3's pure functions in `api/venueflow/routing.py` unchanged unless coordination identifies a specific helper contract defect; do not edit visitor-owned templates or JavaScript. Full organizer publish UI, QR, and visitor-page snapshot rendering remain P4-INT-4 work.
- Shared contract: Use the proposed request `{ "venue_id": "...", "start_node_id": "...", "destination_feature_id": "..." }` from [P3-NAV-5](../../person-3-navigation/phases/P3-NAV-5.md). Success returns `{ "venue_id": "...", "event_id": "...", "version": 1, "route": { "ok": true, "node_ids": [], "edge_ids": [], "distance_m": 0, "duration_s": 0 } }`; a valid unreachable or invalid-length route returns HTTP 200 with the helper's `route.ok: false`, reason, and message. Resolve `destination_feature_id` through the explicit `access_node_id` in that published snapshot. Route graph records pass through to `find_route` as string IDs and existing edge fields. No draft fallback or coordinate/proximity inference is allowed.
- Acceptance criteria:
-  - [x] Each map feature can store an optional explicit `access_node_id`; map-draft writes reject a non-null ID that does not name a path node in the same submitted venue snapshot, and reads return it unchanged.
  - [x] Publishing copies the access-node mapping into the immutable snapshot; later draft edits do not change prior versions.
  - [x] An event-scoped publish API creates a monotonically increasing immutable snapshot containing the event and current venue map collections, including explicit access-node links.
  - [x] `POST /api/route` validates required fields, resolves the venue and its latest published snapshot, and calls the pure routing helper using only that snapshot's graph and destination mapping.
  - [x] Missing venue or published snapshot returns 404; malformed request, unknown start node, unknown destination feature, missing/invalid feature access-node link, or invalid snapshot reference returns a field-specific 400. There is no draft or nearest-node fallback.
  - [x] Valid routes return venue/event/version identity and the helper's route object; unreachable and invalid selected-edge-length outcomes remain explicit `ok:false` route results, without fabricated success.
  - [x] Regression verification covers feature-link persistence and same-venue validation, published version selection, draft mutation isolation, error mapping, and successful/no-route route results.
